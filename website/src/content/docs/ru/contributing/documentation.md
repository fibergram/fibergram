У сайта два слоя: рукописные руководства, которые вы читаете, и справочник API,
сгенерированный из исходников.

## Справочник API генерируется

Каждый публичный экспорт несёт JSDoc, а `pnpm docgen` превращает его в markdown в
`packages/*/docs/modules/`. Дальше `website/scripts/sync-api-reference.mjs`
переписывает этот вывод в коллекцию Starlight: frontmatter Jekyll становится
frontmatter Starlight, самодельное оглавление выбрасывается, заголовки понижаются
на уровень, а ссылки `{@link …}` резолвятся в настоящие перекрёстные ссылки.

Сгенерированные страницы в `src/content/docs/reference/` — **в gitignore**. Не
правьте их: правка исчезнет при следующей синхронизации. Правьте JSDoc в исходниках.

```bash
pnpm docgen              # пересобрать packages/*/docs из исходников
pnpm --filter @fibergram/website sync    # переписать это в сайт
pnpm --filter @fibergram/website dev     # и то, и другое, затем поднять сервер
```

:::note[Сгенерированная поверхность Bot API исключена]
`@fibergram/core/client/generated` — около 5 МБ markdown, механически выведенного
из спеки Telegram. Публикация дала бы три нечитаемых многомегабайтных страницы,
поэтому синхронизация их пропускает и ссылается на
[справочник Telegram](https://core.telegram.org/bots/api).
:::

## Гейт документации

Каждому публичному экспорту нужен JSDoc с:

- коротким описанием,
- **компилирующимся `@example`**,
- `@since`,
- опционально `@category`.

`pnpm docgen` — **гейт в CI**. Не компилящийся `@example` или недокументированный
экспорт валит сборку. Поэтому примерам в справочнике API можно доверять: они
проверены компилятором против настоящих исходников.

```ts
/**
 * An in-memory {@link Dedup} backed by a `Ref<HashSet<number>>`.
 *
 * @example
 * import { Dedup } from "@fibergram/core"
 * import { Layer } from "effect"
 *
 * const layer: Layer.Layer<Dedup.Dedup> = Dedup.layerMemory
 *
 * @category layers
 * @since 0.1.0
 */
```

:::caution[Сниппеты в руководствах не компилируются]
Блоки `@example` в справочнике API проверяются компилятором, а сниппеты в этих
рукописных руководствах — нет. Добавляя новый, копируйте его из проходящего теста
или из `@example`, а не пишите по памяти; и лучше сослаться на справочник, чем
пересказывать сигнатуру, которая потом разъедется.
:::

## Граница именования

Bot API говорит на `snake_case`. fibergram — нет.

`snake_case` допустим **только** внутри определений краевых схем в
`packages/core/src/client`, где `Schema.encodeKeys` переводит
`snake_case → camelCase` при декоде и обратно при энкоде. Везде остальном —
хендлеры, тесты, руководства, примеры — camelCase.

`snake_case` за пределами этой границы это баг, а не «поле из API». Документации
это тоже касается: написав `retry_after` в руководстве, вы обучаете неверной
модели, поэтому пишите `retryAfter`, а имя из провода упоминайте, только когда речь
идёт о проводе.

## Как писать руководства

Руководства живут в `website/src/content/docs/`. Английский — локаль по умолчанию
и лежит в корне; русский — в `ru/` с теми же путями.

- **Внутренние ссылки** абсолютны и заканчиваются слешем: `/concepts/dialogs/`. В
  русских страницах они несут локаль: `/ru/concepts/dialogs/`.
- **Отсутствующий перевод — это нормально.** Starlight откатывается к английской
  странице и показывает пометку «не переведено», поэтому страница только на
  английском не ломает русский сайт.
- **Пункты сайдбара** живут в `astro.config.mjs`, локализованные подписи — в
  `translations`. Новой странице нужна запись там: руководства намеренно не
  автогенерируются, потому что важен порядок чтения.

## Changesets

Изменения публичного поведения едут с changeset:

```bash
pnpm changeset
```

Изменениям только в документации он не нужен.

## Как гонять проверки

```bash
pnpm build          # tsc -b по графу проекта
pnpm typecheck      # src и test в каждом пакете
pnpm test           # vitest
pnpm lint           # eslint с типовой информацией
pnpm docgen         # гейт документации
pnpm circular       # madge
pnpm check:exports  # attw
```

CI гоняет всё это на каждом пул-реквесте.
