## Один контракт

Оба транспорта делают одно и то же: **производят в ограниченную `Queue<Update>` и
отдают наружу `Stream.fromQueue` над ней**. Диспетчер дренит этот стрим и не
знает, какой транспорт его наполнил.

```ts
// long polling
const updates = yield * Polling.make()

// вебхук
const webhook = yield * Webhook.make({ secretToken: "s3cret" })
const updates = webhook.updates

// в любом случае:
yield * Dispatcher.run({ updates, dialog })
```

Семантика коммита — единственное, что действительно транспорт-специфично, —
остаётся внутри транспорта: оффсет у поллинга, HTTP-статус у вебхука. Выше очереди
не меняется ничего.

Поэтому смена транспорта — правка в одну строку, а тесты скармливают
`Updates.stream([...])` тому же диспетчеру.

## Long polling

```ts
Polling.make(options?): Effect<Stream<Update>, never, TelegramClient | Scope>
```

Создаёт очередь, форкает цикл опроса в амбиентный `Scope` и сразу возвращает
стрим. Цикл зовёт `getUpdates(offset)`, оффертит батч и коммитит
`max(updateId) + 1`.

| Опция | По умолчанию | Комментарий |
|---|---|---|
| `timeout` | 30 | Таймаут long poll в секундах. |
| `limit` | 100 | Максимум апдейтов в батче. |
| `allowedUpdates` | — | Передавайте `Router.allowedUpdates(router)`. |
| `errorBackoff` | 1 с | Пауза после сбоя, не связанного с рейт-лимитом. |
| `capacity` | 1024 | Ограниченная очередь; заполнение включает back-pressure на опрос. |
| `offsetStore` | — | Персистентный оффсет между рестартами. |

**Цикл никогда не умирает.** `RateLimited` усыпляет на `retryAfter`, удерживая
оффсет; любой другой сбой пишет предупреждение и ретраится через `errorBackoff`.
Состояния, в котором бот молча перестал получать апдейты, не существует.

### Durable-оффсет

```ts
interface OffsetStore {
  readonly load: Effect<Option<number>> // сидит оффсет при старте
  readonly commit: (offset: number) => Effect<void> // после постановки батча в очередь
}
```

Без стора оффсет — `Ref` в памяти: после рестарта бот перечитает то, что Telegram
ещё держит, и dedup это поглотит. Со стором бот продолжает ровно с того места, где
остановился. Провал коммита логируется и не роняет цикл, потому что перекрытие в
любом случае поглощает dedup.

## Вебхуки

```ts
const webhook = yield * Webhook.make({ secretToken: "s3cret" })
```

`Webhook` отдаёт три вещи:

- `updates` — тот же контракт `Stream<Update>`,
- `handle(request): Promise<Response>` — веб-стандарт для serverless, Bun, workerd
  и Hono,
- `httpApp` — Effect-нативный роут для серверов на `@effect/platform`.

Оба входа исполняют одно и то же транспорт-нейтральное решение:

1. **Сравнение за постоянное время** заголовка
   `X-Telegram-Bot-Api-Secret-Token`. Несовпадение или отсутствие → `401`.
2. **Декод** тела через `Schema`. Кривое тело от *аутентифицированного* источника
   пишет предупреждение и отвечает `200` — намеренно, чтобы не спровоцировать
   шторм ретраев.
3. **Offer** в очередь → `200`.

Всё происходит внутри span'а `fibergram.webhook`.

### Fast-ack против durable-ack

Telegram ретраит вебхук, на который не получил `2xx`, поэтому тяжёлая работа в
HTTP-хендлере невозможна — только offer и подтверждение:

| Режим | Поведение | Риск |
|---|---|---|
| **fast-ack** (по умолчанию) | offer → `200` | Падение между `200` и обработкой теряет апдейт. |
| **durable-ack** (`persist`) | `persist(update)` → offer → `200`; провал persist → `500` | Telegram переотправит; dedup по `updateId` уберёт дубль. |

```ts
Webhook.make({
  secretToken: "s3cret",
  persist: (update) => appendToLog(update)
})
```

Это выбор на уровне `Layer`, а не правка в хендлерах.

Практические детали, адаптеры фреймворков и несколько ботов на одном эндпоинте —
в [Вебхуках](/ru/guides/webhooks/).

## Гарантии доставки

Практическая обработка ровно один раз складывается из двух независимых механизмов:

1. **Durable-оффсет** (поллинг) или **переотправка Telegram** (вебхук) — апдейт не
   теряется.
2. **`Dedup.seen(updateId)`** — единственный атомарный `Ref.modify` над `HashSet` —
   апдейт не обрабатывается дважды.

По отдельности ни того, ни другого не хватает; вместе они превращают доставку
at-least-once в поведение exactly-once.

:::caution[`Dedup.layerMemory` забывает при рестарте]
Множество dedup в памяти не переживает перезапуск процесса, поэтому перекрывающая
переотправка сразу после деплоя может обработаться дважды. Подложите durable-стор,
если двойная обработка для вашего бота недопустима.
:::

## Порядок

Диспетчер дренит входной стрим **последовательно** — отсюда упорядоченность
приёма. Дальше он отдаёт каждый апдейт `EntityManager`, который гарантирует
порядок *внутри* адреса (один мейлбокс, один fiber), выполняя разные адреса
параллельно. См.
[Архитектуру](/ru/concepts/architecture/#рантайм-сверху-вниз).
