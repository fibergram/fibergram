Память диалога — **решение уровня проводки**. Во всех трёх режимах ниже работает
один и тот же код хендлера; меняется массив, который вы передаёте в
`Effect.provide`.

## Три режима

### Эфемерный

```ts
Effect.provide([DialogStore.layerMemory, Dedup.layerMemory])
```

Состояние живёт в `Ref` ровно столько, сколько процесс. Диалоги остаются горячими
в памяти навсегда — ничего не вытесняется и никуда не записывается. Подходит для
ботов из одних команд и для тестов.

### Горячий, но персистентный

```ts
import { PersistedDialogStore } from "@fibergram/durable"
import { KeyValueStore } from "effect/unstable/persistence"

Effect.provide([
  PersistedDialogStore.layer.pipe(Layer.provide(KeyValueStore.layerFileSystem("./.data"))),
  Dedup.layerMemory
])
```

Каждый переход состояния снапшотится в JSON под префиксом `"fibergram:dialog:"`.
Недозаполненный визард переживает деплой. Диалоги по-прежнему держатся в памяти
между апдейтами, поэтому бот с миллионом чатов держит миллион записей.

### Пассивируемый

```ts
import { PassivatingEntityManager, PersistedDialogStore } from "@fibergram/durable"

PassivatingEntityManager.run({ updates, dialog }).pipe(
  Effect.scoped,
  Effect.provide([PersistedDialogStore.layer, Dedup.layerMemory])
)
```

`PassivatingEntityManager.run` заменяет `Dispatcher.run`. Простаивающие диалоги
вытесняются из памяти через `passivateAfter` (по умолчанию 5 минут) и прозрачно
рехидрируются из стора на следующем апдейте. Это режим для долгих разговоров на
масштабе: многодневный цикл ходов RPG между ходами не стоит ничего.

## Что гарантирует каждый

| | Эфемерный | Персистентный | Пассивируемый |
|---|---|---|---|
| Переживает падение хендлера | ✅ | ✅ | ✅ |
| Переживает рестарт | ❌ | ✅ | ✅ |
| Ограниченная память при множестве диалогов | ❌ | ❌ | ✅ |
| Порядок внутри чата | ✅ | ✅ | ✅ |
| Дополнительная задержка на холодном апдейте | — | — | одно чтение из стора |

## Почему пассивация остаётся корректной

Вытеснение и доставка гоняются по природе. Гонку снимают два механизма:

- **Кооперативная эвикция.** Адресный fiber сам меряет простой через
  `Effect.timeoutOption(Queue.take, passivateAfter)` и снимает *себя* с горячего
  множества, если очередь пуста. Работающий хендлер никогда не прерывают.
- **Per-address latch, который эвикция никогда не чистит.** И `send`, и
  самоэвикция берут один и тот же `Semaphore` перед тем, как трогать запись
  мейлбокса, поэтому они сериализуются, а апдейт, пришедший посреди рехидрации, не
  теряется.

Эвикция освобождает fiber, а не состояние — состояние уже лежит в сторе.

## Durable-таймеры

`Effect.sleep` — неподходящий инструмент для «напомнить через три дня»: fiber
умрёт вместе с процессом. `DurableTimer` вместо этого персистит абсолютный дедлайн:

```ts
import { DurableTimer } from "@fibergram/durable"

const armNextTurn = (address: DialogAddress.DialogAddress) =>
  Effect.gen(function* () {
    const timer = yield* DurableTimer.DurableTimer
    yield* timer.schedule({ address, key: "next-turn", delay: "3 days" })
  })
```

При старте каждый ожидающий таймер перечитывается и перевзводится на *остаток*;
просроченные срабатывают немедленно. Планирование идемпотентно по
`(address, key)`.

:::caution[Срабатывание at-least-once]
Падение между срабатыванием и удалением записи приведёт к повторному
срабатыванию. Держите `onFire` идемпотентным.
:::

## Что стоит знать до того, как решитесь

- **Состояние должно круглиться через JSON.** Для снапшотов корутин это верно;
  для decider'ов, написанных руками, проверьте. `Date`, `Map` или экземпляр класса
  не переживут круг нетронутыми.
- **Миграций схемы пока нет.** Стор, записанный старой версией типа состояния,
  прочитается как есть. Версионируйте форму состояния сами, если планируете её
  менять.
- **Сбои стора — это defect'ы.** Канал ошибок порта `DialogStore` — `never`,
  поэтому провал записи всплывает через супервизор на границе адреса, а не как
  типизированная ошибка, которую хендлер обязан ловить. См.
  [Ошибки](/ru/concepts/errors/#модель-отказов-у-портов).
- **Корутины реплеятся.** В durable-режиме генератор перезапускается с нуля на
  каждом апдейте. Именно это делает его возобновляемым и именно поэтому
  недетерминированные значения должны приходить через `d.run`. См.
  [Разговоры](/ru/guides/conversations/).

## Бэкенды

`PersistedDialogStore` написан против `KeyValueStore` из
`effect/unstable/persistence`, поэтому выбор хранилища — ещё один слой ниже:

```ts
KeyValueStore.layerMemory //          тесты
KeyValueStore.layerFileSystem(dir) // однонодовые боты
KeyValueStore.layerSql //             всё серьёзное
```

Тот же `KeyValueStore` обслуживает [`@fibergram/chat-members`](/ru/guides/chat-members/),
а в [примере restaurant-booking](https://github.com/fibergram/fibergram/tree/main/examples/restaurant-booking) —
ещё и собственные репозитории приложения: одно решение о хранилище на весь бот.

:::note[Это пакет с максимальным риском]
`@fibergram/durable` намеренно единственный трогает периметр persistence из
Effect v4, который пока движется. Этот размен и держит `@fibergram/core`
стабильным — см.
[волатильный периметр](/ru/concepts/architecture/#волатильный-периметр).
:::
