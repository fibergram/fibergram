## Принцип проектирования

fibergram не строит параллельную вселенную поверх Effect. Там, где у Effect уже
есть ответ, этот ответ и становится API:

| Задача | Ответ Effect | Что делает fibergram |
|---|---|---|
| Зависимости | `Layer` + `Context.Service` | Порты (`DialogStore`, `Dedup`, `TelegramClient`) — сервисы; слои подключаете вы. |
| Ошибки | типизированный канал `E` | `TelegramError` — тегированный union в `E`; ваши ошибки текут нетронутыми. |
| Конкурентность | fiber'ы и `Scope` | Один долгоживущий fiber на адрес диалога, форкнутый в амбиентный скоуп. |
| Стриминг | `Stream` | Ингест производит `Stream<Update>`, диспетчер его дренит. |
| Валидация | `Schema` | На каждом I/O-краю: апдейты, аргументы команд, payload кнопок, персистентное состояние. |
| Время | `Clock` | Любая задержка и таймаут, поэтому в тестах ими крутит `TestClock`. |

Ни цепочки middleware, ни реестра плагинов, ни объекта контекста. Композиция —
это композиция Effect.

## Рантайм сверху вниз

```
 транспорт                 диспатч                        ваш код
┌──────────────┐   ┌──────────────────────────┐   ┌────────────────────┐
│ Polling      │   │ Dedup (updateId)         │   │ Dialog / Coroutine │
│   или        │──▶│ KeyExtractor → адрес     │──▶│ роуты Router       │
│ Webhook      │   │ мейлбоксы EntityManager  │   │ аксессоры Chat.*   │
└──────────────┘   └──────────────────────────┘   └────────────────────┘
   Queue<Update>       один fiber на адрес            Effect<A, E, R>
```

1. Транспорт производит в ограниченную `Queue<Update>` и отдаёт наружу
   `Stream.fromQueue` над ней. Polling и webhook здесь взаимозаменяемы — см.
   [Ингест](/ru/concepts/ingestion/).
2. `Dispatcher.run` дренит этот стрим **последовательно** — отсюда берётся
   упорядоченность приёма.
3. Каждый апдейт дедуплицируется по `updateId`, затем отображается в
   [`DialogAddress`](/ru/concepts/dialogs/#адрес) подключаемым экстрактором ключа.
4. `EntityManager` держит `HashMap<key, Queue<Update>>` и **один долгоживущий
   fiber на адрес**, дренящий свою FIFO-очередь. Порядок гарантирован внутри
   адреса, разные адреса работают параллельно.
5. Перед запуском хендлера диспетчер выставляет амбиентный
   [контекст апдейта](/ru/concepts/no-ctx/) и телеметрический span, после чего
   вызывает `decide` диалога.

Полный контракт конкурентности: **один мейлбокс на адрес, один fiber на мейлбокс,
атомарный dedup и per-address latch, переживающий пассивацию**, — чтобы гонка
между эвикцией и доставкой не потеряла апдейт.

## Раскладка пакетов

Граница проведена по **реальному бета-риску и темпу релизов**, а не по концептам.
Низкорисковый периметр живёт *внутри* `@fibergram/core` как subpath-модули —
так же, как сам `effect` поставляет один пакет со множеством модулей:

| Пакет / subpath | Ответственность | Риск v4 |
|---|---|---|
| `@fibergram/core` | `Dialog`, decider, `Decision`, `EntityManager`, экстрактор ключа, `Router`, `Chat`, типизированные ошибки, `CallbackData`, `Session` | низкий |
| `@fibergram/core/client` | `TelegramClient` (Tag + Layer поверх `HttpClient`), схемы Bot API, `InputFile`, `Transform` | низкий |
| `@fibergram/core/polling` | long polling и управление оффсетом | низкий |
| `@fibergram/core/testing` | `TestTelegram`, синтетические апдейты | низкий |
| `@fibergram/core/ui` | клавиатуры, форматирование `Fmt`, типизированные `Emoji`, `Reaction` | низкий |
| `@fibergram/webhook` | HTTP-ингест и проверка secret-токена, адаптеры Express/Fastify | средний |
| `@fibergram/durable` | персистентные диалоги, durable-таймеры, пассивация | **высокий** |
| `@fibergram/menu` | инлайн-меню с состоянием поверх `CallbackData` и `DialogStore` | низкий |
| `@fibergram/i18n` | переводчик на Fluent с амбиентной локалью | низкий |
| `@fibergram/chat-members` | кэш членства поверх `KeyValueStore` | средний |

Направление зависимостей строго одностороннее: всё строится на
`@fibergram/core`, а сам `core` зависит только от `effect`.

:::note[Почему `client` не отдельный пакет?]
Изначально он им был. «Пакет на концепт» стоил шести наборов конфигов tsconfig,
eslint, docgen и changeset и не давал ничего: `client`, `polling`, `testing` и
`ui` — низкорисковый код, релизящийся в такт с ядром. Изоляция сохранена ровно
там, где окупается, — вокруг `durable`.
:::

## Волатильный периметр

Effect v4 — в бете. **Модель** — `Effect`, `Layer`, `Schema`, `Stream` — стабильна
и практически не отличается от v3. Двигается периметр: `@effect/platform`
растворился в `effect/unstable/http`, `FiberRef` уступил место
`Context.Reference`, а модули persistence, workflow и cluster ещё формируются.

Ответ fibergram — структурный:

- **`effect` запинен точной бета-версией.** Без каретки. Апгрейды осознанные, по
  одному changelog за раз.
- **`core` никогда не импортирует `effect/unstable/persistence`.** Он определяет
  собственные порты (`DialogStore`, `Dedup`, `CallbackStore`) с реализациями в
  памяти.
- **`@fibergram/durable` принимает изменчивость на себя.** Он реализует те же
  порты поверх `KeyValueStore` и по замыслу несёт наибольший бета-риск в
  монорепозитории, чтобы `core` оставался публикуемым и полезным.
- **`@fibergram/chat-members` — отдельный пакет** ровно по той же причине: ему
  нужен периметр persistence, которого `core` избегает.

Если cluster в Effect приземлится неожиданным образом, изменится один пакет.

## Что это даёт

Постоянная выгода в том, что **поведенческие решения становятся решениями
проводки**:

```ts
Effect.provide([
  DialogStore.layerMemory, //  ← в памяти либо PersistedDialogStore.layer
  Dedup.layerMemory,
  TelegramClient.layer //      ← настоящий клиент либо tg.layer из TestTelegram
])
```

Режим персистентности, транспорт, политика ретраев, пейсинг под flood-лимиты и
весь тестовый дублёр выбираются здесь. Ни один хендлер выше этой строки не
меняется, когда меняется что-то из них.
